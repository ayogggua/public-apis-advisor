# 选定后的接入、部署与验收

仅在用户选定并授权实施，或明确授权代选并实施后使用。既有授权持续有效，不因进入本文件再次确认。当前用户和项目规范优先；不强制用户采用特定语言、框架、接口风格或云平台。

## 把选择变成明确的工作范围

确定所选服务、要交付的功能、目标环境、已接受的成本/数据处理条件。只补问必要缺口，例如缺少部署目标或需要用户提供凭证。先完成不依赖这些信息的接口适配和配置准备，不把用户引向一串泛化审批。

选定供应商不等于批准购买套餐、迁移生产数据、公开部署或发送通知。实施中出现原建议未覆盖的新增成本、数据去向或部署目标变化，先说明具体影响，再获取这项变化的决定。不要扩大范围去替换同类既有系统。

## 按实际服务形态实施

| 形态 | 需要落实的工作 | 不应混淆的边界 |
| --- | --- | --- |
| 第三方托管 API | 注册/凭证由用户控制；按官方接口接入现有服务层，配置超时、限流和错误处理 | 只能部署自己的调用方或代理，不能宣称部署了供应商服务本体 |
| 开源可自建服务 | 检查对应仓库/版本、许可、数据和运行依赖，再使用项目认可的部署方式 | 有源代码或免费额度不代表其数据、模型权重及托管资源免费 |
| MCP | 区分远程连接与本地服务，检查来源和权限，只在用户指定客户端配置 | MCP 接入不等于应用后端已经拥有相应 HTTP 接口；发现阶段不安装 |
| 数据集/静态数据 | 下载获准数据，按更新频率与许可导入、缓存或同步 | 不虚构实时服务、持续更新或可再分发权 |

优先复用项目已有客户端、供应商适配器和密钥管理。少量 HTTP 调用不必安装整套 SDK。尊重现有数据库和路由约定；供应商既定路径按其文档调用，不为了统一内部风格改写外部协议。

密钥放既有安全配置中，不写前端、提交记录或日志。向第三方发送真实用户资料前确认任务授权包含该数据用途；对照试用优先使用公开或合成的最小输入。

仅对适合重试的请求做有限重试，遵守 `Retry-After`。支付、通知、创建资源等有副作用操作必须考虑幂等和重复执行，不能用“再试一次”反复触发。缓存与结果保存遵循供应商许可和项目数据策略。

对自建部署，复用已有部署流程，核对资源、网络、存储和回退方式。需要生产发布批准时，先把可审阅的改动、已完成的本地验证和具体发布步骤准备好，再请求最后一步批准；用户已经授权同一目标的部署则继续完成。

## 用最小而真实的验证确认交付

- 运行项目现有的相关检查；遵守用户对新增测试、迁移脚本和文档的限制，不自动产生这些文件。
- 在已批准的环境，用最小调用确认鉴权、返回结构和目标功能；付费请求遵守已同意的预算。缺少凭证时完成配置入口并明确尚未验证，不伪造成功结果。
- Mock/样本只能证明本地处理逻辑，不能证明真实服务、额度、网络或部署已通过。
- 部署成功后继续检查目标环境的进程/健康状态和实际功能；只有目标包含公网访问时才检查公网入口。一个成功的 HTTP 状态或部署工具返回值不足以证明业务功能正常。
- MCP 验证确认客户端识别及已授权的最小只读调用；不要以发送消息、付款或修改真实数据作为默认验收方式。
- 回报修改范围、使用环境、真实验证结果和剩余问题。上线未完成就明确说未完成，不将本地就绪写成生产可用。
